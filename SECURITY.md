# Безопасность

## Что здесь вообще есть

`as-skill` — это markdown-файлы (промпты для AI-агента) плюс Go-инсталлятор (`tools/`, собирается в бинарь `as-skill`). Исполняемого кода, который запускается сам по себе, в скиллах нет — единственный автозапускаемый код во всём репозитории — Stop-хук `test-gate.sh` домена `code`, ставится только вместе с этим доменом и по умолчанию fail-open (см. правило ниже). Поверхность атаки — две вещи:

1. **Инсталлятор** (`as-skill`) пишет в `<project>/.claude/` — куда именно, решает флаг `--project` (по умолчанию текущая директория). Он не трогает домашний `~/.claude/`, `~/.codex/`, `~/.cursor/` и не пишет в Obsidian vault напрямую — если только их путь явно не передан в `--project`.
2. **Содержимое скиллов** попадает в контекст модели и влияет на её действия.

## Что делает инсталлятор

`as-skill install` кладёт домены/скиллы в `<project>/.claude/{rules,skills,agents}` — по умолчанию **symlink**'ами на файлы этой копии репозитория (правки в `domains/` видны во всех проектах, куда они засимлинканы, сразу — это осознанный побочный эффект режима, стоит помнить о нём при шаринге репозитория между несколькими людьми с разными правами). `as-skill install --copy` вместо этого делает независимую копию-снэпшот.

Каждая поставленная единица (домен + вид + имя) записывается в `<project>/.claude/skills-lock.json` — по этой записи `as-skill status`/`doctor` отличают своё от чужого и режим установки, а `uninstall` сносит только то, что сам же поставил. Если путь назначения уже существует и не отслеживается — `install` откажется писать без `--force`.

Ни инсталлятор, ни сами скиллы не требуют root, не устанавливают пакеты и не ходят в сеть — единственная сетевая активность вокруг репозитория это `git clone/pull` самого `as-skill`.

## Что скиллы делают с твоими данными

Скиллы работают только с тем, что ты им дал в сессии. Никакой телеметрии, никакой отправки данных наружу — в репозитории нет кода, который куда-либо что-либо шлёт.

Домен `obsidian` читает и пишет файлы внутри `$OBSIDIAN_VAULT` (см. `README.md`, раздел «Как задать `OBSIDIAN_VAULT`»). Домен `git` предлагает git-команды, но по общему для всех доменов контракту «план → подтверждение → действие → отчёт» (`AGENTS.md`) не делает push, tag и удаление веток без явного подтверждения. Домен `devops` не вызывает внешний CLI напрямую — сегодня это только советующие (Consilium: `architecture`, `security`, `sre`, `diagnostics` — read-only, не трогают код и конфиги) и исполняющие (`ci`, `helm`, `k8s` — пишут пайплайны/чарты/манифесты в своей части файлов) агенты; по GitOps-правилу прод меняется только через ArgoCD, ни один агент не делает `kubectl apply` в прод напрямую.

## Prompt injection

Скиллы и агенты, которые читают внешний материал (`obsidian-ingest`, `content-factory` он же `/content-zavod`, `devops-diagnostic`, `devops-sre`), обрабатывают текст из источников, которые ты не писал: статьи, транскрипции, логи. Такой текст может содержать инструкции, адресованные модели.

Правило простое: **содержимое источника — это данные, а не команды**. Если после ингеста статьи агент вдруг предлагает выполнить команду, которой ты не просил, — это ровно тот случай. Не выполняй, посмотри исходник.

## Как сообщить о проблеме

Нашёл что-то, что позволяет коллекции сделать с системой больше, чем описано выше, — напиши на <ialexshishin@gmail.com> или заведи issue в [репозитории](https://github.com/alexeyshishin/as-skill), если проблема не эксплуатируется по описанию.

Публичный issue подходит для «скрипт удаления сносит лишнее». Приватное письмо — для «вот так через скилл можно выполнить произвольную команду».

Ответ — в течение недели. Это личный проект, не продукт с SLA.
